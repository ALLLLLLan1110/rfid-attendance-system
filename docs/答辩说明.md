# RFID 一卡通考勤系统答辩说明

这份说明对应当前真实代码，不能只背结论。答辩前应打开所列文件，逐段说明输入、判断、数据库变化和异常分支。

## 1. 读卡器如何与程序通信？波特率有什么作用？

KL9007U 通过 CP210x 把 USB 转换成虚拟串口 COM。`reader-bridge/Program.cs` 使用厂家 32 位 DLL 打开串口，`baud = 5` 是厂家接口对 57600 bps 的枚举值。波特率规定串口每秒传输的符号速率；两端设置不一致会导致无法通信或解析出乱码。

Node.js 是 64 位，不能直接加载 32 位厂家 DLL，所以系统把硬件通信放进单独编译为 x86 的 `KL9007ReaderBridge.exe`。桥接程序把硬件事件输出成“一行一个 JSON”，`lib/reader-service.js` 启动子进程并解析标准输出。这样既解决 DLL 位数问题，也把硬件异常与 Web 服务隔离。

## 2. 原始卡号是什么格式，怎样提取和过滤？

读卡器使用 EPC Class 1 Gen 2。厂家 `Inventory_G2` 返回字节缓冲区：每个标签先给出 EPC 字节长度，后面是 EPC 字节。`Program.cs` 的 `InventoryOnce` 按长度移动 offset，`BytesToHex` 把每个字节格式化成两位大写十六进制，例如字节 `E2 00 00 17` 变成字符串 `E2000017`。

过滤分三层：

1. C# 层检查长度和缓冲区边界，避免越界解析。
2. `lib/reader-service.js` 只接收能解析为 JSON 且 `type` 合法的事件。
3. `lib/card.js` 的 `normalizeCardUid` 去空格、转大写，并只允许 8–64 位偶数长度十六进制；非法值返回 `null`，不会进入业务数据库。

## 3. 数据库有哪些表，主键怎样设计？

当前考勤业务使用两张表：

- `students`：`id` 是内部主键；`student_no` 和 `card_uid` 分别唯一；另有姓名、班级、状态和创建时间。
- `attendance_records`：`id` 是记录主键；`student_id` 是指向学生的外键；另有刷卡时的卡号快照、签到时间、签退时间和在校分钟数。

不用姓名当主键，因为姓名可能重复和修改；不用卡号直接做所有表的主键，因为学生换卡后历史记录仍应关联同一个学生。数据库还有部分唯一索引，保证同一学生最多一条 `check_out_at IS NULL` 的未签退记录。

旧版网吧业务表仍保留在原数据库里以避免破坏历史数据，但当前考勤代码不会读写它们。

## 4. 如何判断本次刷卡是签到还是签退？

入口是 `server.js` 的 `processCard(uid)`：

1. 根据 `card_uid` 查询学生；查不到返回陌生卡，完全不写考勤。
2. 查询该学生按 id 倒序的最近一条考勤记录。
3. 调用 `lib/attendance.js` 的 `decideAttendanceAction`。
4. 没有最近记录，或最近记录已有 `check_out_at`：返回 `check_in`，插入新记录。
5. 最近记录没有 `check_out_at`：返回 `check_out`，更新同一条记录的签退时间和分钟数。
6. 整个判断与写入放在 `BEGIN IMMEDIATE` 事务中，避免两个请求同时改变状态。

## 5. 为什么快速重复刷卡会产生脏数据，怎样防护？

UHF 读卡器会持续盘存，卡片停在天线前可能每几百毫秒被读到一次。如果每次硬件读数都直接执行签到/签退，就会在几秒内反复切换状态。

系统有三层防护：

- 硬件桥接：`ActiveCards` 保存仍在感应区的 EPC，同一卡停留时只发一次事件；离开约 3 秒才允许再次触发。
- 业务服务：最近有效操作不足 `MIN_ACTION_INTERVAL_SECONDS`（当前 10 秒）时返回 `duplicate`，不执行 INSERT 或 UPDATE。
- 数据库：部分唯一索引阻止同一学生同时存在两条未签退记录。

防重复必须放在服务端，不能只在按钮上做节流，因为真实读卡事件、手工输入、模拟接口或两个浏览器都可能绕过前端限制。

## 6. 现场需求：签到和签退间隔不能小于 30 分钟，怎样修改？

当前最小间隔常量在 `lib/attendance.js`：

```js
export const MIN_ACTION_INTERVAL_SECONDS = 10;
```

改成：

```js
export const MIN_ACTION_INTERVAL_SECONDS = 30 * 60;
```

业务判断已经统一使用这个常量，所以服务端会在签到后 30 分钟内返回 `duplicate`，不会签退。还应同步：

1. 把前端“10 秒防重复”文案改成“30 分钟最小间隔”。
2. 修改 `test/attendance.test.js`，增加 29 分 59 秒被拦截、30 分钟允许签退两个边界测试。
3. 运行 `npm test`，再用测试数据库验证记录条数不变。

不要只改前端倒计时，因为直接调用 API 仍可绕过。

## 7. 建议现场演示顺序

1. 展示顶部 COM3 已连接、固件和 8 dBm 功率。
2. 刷陌生卡：证明有提示、不崩溃、不写考勤。
3. 登记该卡：填写学号、姓名、班级，提交后自动签到。
4. 10 秒内再刷：证明重复请求被忽略，历史记录没有增加。
5. 超过 10 秒再刷：自动签退，原记录补充签退时间和时长。
6. 使用姓名或日期查询历史记录。
7. 拔掉 USB：Web 页面仍可操作并显示通信异常；插回后重连。
8. 打开 `lib/attendance.js`，现场把间隔改成教师指定值并运行测试。
